#FSM 不是 200 时爬梯（仅正常模式可行）

先读 status 的两行，它们决定你从哪一级起步、走哪条分支：

        FSM ID: code=0  value=0   <- ZeroTorque 零力矩 (全身瘫软, 必须吊着)
  躯干姿态: roll=+0.027 pitch=-0.005 yaw=-0.838 rad   -> 直立
  • code=0 = 运控服务在跑（code=3102 是调试模式，见本节末尾）
  • value = 现在在哪一级
  • 躯干姿态 那行的结论字（直立 / 倾斜 / 趴着躺着）决定用 prepare 还是 lie2stand （由 pitch 判定：|pitch|<0.35 直立，>1.0 趴着/躺着）
FSM 含义 机器人现在 下一条命令
0 ZeroTorque 零力矩，全身瘫软 必须吊着 / 趴着 damp
1 Damp 阻尼态（安全停靠态） 可以吊着 prepare（直立）/ lie2stand（趴着）
2 / 3 / 4 蹲下 / 坐下 / 站立锁定 脚在地上 start
200 主运控，arm_sdk 可用 站着 不用爬

第 1 步 · damp（腿不动，这一步安全）

cd ~/zh
python3 g1_ctl.py damp

FSM 0 → 1。不在 DANGEROUS 集合里，不问确认、腿不会动 —— 只是给关节加 阻尼，机器人不再完全软、姿态能大致撑住。

零力矩下直接跳 prepare 会被脚本挡掉： [!] 当前是零力矩(0), 不能直接跳站立锁定。先跑 g1_ctl.py damp。

第 2 步 · 动手：把脚放到地上（没有命令）

damp 之后把机器人降下来，让双脚踏实着地；吊装带留着但放松，只当防坠、 不承重。

下面两步是要它自己站起来并承重的。脚不着地的话，腿只是在空中伸展， 到不了预期状态。

第 3 步 · prepare → start

python3 g1_ctl.py prepare     # → FSM 4 站立锁定   ⚠️ 腿会动
python3 g1_ctl.py start       # → FSM 200 主运控   ⚠️ 站起来
python3 g1_ctl.py status      # 确认真的是 200

机器人是趴着/躺着的话，第 3 步第一条换成 python3 g1_ctl.py lie2stand（趴→站，FSM 702），之后同样 start。

这两条都在 DANGEROUS 里，会弹确认框：

  即将执行: prepare   (当前 FSM=1 Damp 阻尼态)
  这会让【腿】动。确认:
    - 物理急停按钮伸手能按到
    - 机器人周围 2 米内没有人和障碍物
    - 如果机器人是吊着的, 吊具能承重且不会卡住
  输入大写 YES 继续, 其它任何输入都会取消:
  • 必须输入大写 YES，小写或直接回车都会取消
  • 别加 --yes 跳过
  • 每条执行完会等 1 秒复查，打印 [+] 完成。FSM: 1 -> 4 (...)。 看到目标级数再敲下一条，别连着贴三行进去

一眼看全

FSM 0  ──damp──>  FSM 1  ──[动手: 把脚放到地上]──>  ──prepare──>  FSM 4  ──start──>  FSM 200
零力矩            阻尼态                                          站立锁定          主运控
瘫软吊着          腿不动、不问确认                                ⚠️腿会动          ⚠️站起来
                                                （趴着的话这里换 lie2stand）

⚠️ 全程周围清空 2 米。整条梯子等价于遥控器 L2+B → L2+↑ → R1+X。

不能跳级，脚本会挡：FSM 0 时 prepare 被拒；start 只接受 FSM 1/2/4/706。

start 源码上也接受 FSM 1（可以从阻尼态直接起身），但还是走 prepare 那一级 —— 脚本自己的提示就是「顺序应该是 damp(1) → prepare(4) → start(200)」， 先锁定站姿再进主运控，比从阻尼态直接起身可控。

到 200 之后

接收端不带 --mode 就是 armsdk：

~/zh/start.sh --hand both --hand-haptic --hand-touch-hz 10

软件急停这时候才是真管用的 —— 再开一个 SSH 窗口（终端 D）停在这条上不回车：

cd ~/zh && python3 g1_ctl.py damp

调试模式下它失效，正常模式下不是。遥控器 L2+B 同样恢复可用。

code=3102 时爬不上去 —— 调试模式的定义就是停掉运控服务，而这些指令全是 发给它的（遥控器走同一条链路，所以那时遥控器也是失效的）。要么退出调试模式， 要么吊装走 --mode lowcmd。

怎么退出调试模式：仓库里没记。最稳的是重启机器人（运控服务会自启）； 否则「当初怎么进的就怎么退」。

#⚠️ 走 lowcmd 时逐条确认

  1. 机器人必须吊装悬空。
  2. 软件急停和遥控器都失效，唯一的急停是物理按钮。
  3. 标定质量门是关的，按空格不会有任何拦截。第一次先小幅度动。

常规：电量 > 50%、遥控器在手边、人离开手臂摆动范围和手指抓握范围。

#1.3 · 急停：出事了按什么

开工前先把这一节读完，出事时没时间翻文档。

#三条急停路，可靠性从高到低

# 手段 正常模式 调试模式 走什么链路
1 物理急停按钮 ✅ ✅ 硬件断电，不经过任何软件
2 遥控器 L2+B ✅ ❌ 失效 DDS → 运控服务
3 终端 D g1_ctl.py damp ✅ ❌ 失效（返回 3102） DDS → 运控服务（和 2 同一条）

2 和 3 走的是同一条链路 —— 网线一松、WiFi 一抖就到不了，运控服务停了就更没用。 它们不是物理急停的替代品，是「手边更近的那个」。

⚠️ 走 --mode lowcmd 时 2 和 3 全部失效，唯一的急停是物理按钮。 这是 「能用 armsdk 就别用 lowcmd」的主要理由。

#开工前先摆好终端 D

正常模式下多开一个 SSH 窗口，停在这条命令上不回车：

ssh unitree@192.168.3.78
cd ~/zh && python3 g1_ctl.py damp

damp 不在 DANGEROUS 里，不问确认、敲下去立刻生效，这正是它能当急停的原因。

⚠️ damp 会让机器人瘫下去。 关节进阻尼态、失去平衡控制，站在地上的话会 顺势坐/倒下去（阻尼让它是沉下去而不是自由落体，但仍然会倒）。这是急停该有的 样子，不是故障 —— 所以只在真出事时用，别拿它当「暂停」。

#按症状选

出什么事 按什么
全面失控 / 上面都来不及 物理急停按钮
手臂乱动、动作明显不对 遥控器 L2+B；或终端 D 回车；或终端 A Ctrl+C
只是想让手臂停下来（不是出事） 终端 B 按 空格 —— 暂停跟随，手臂以 0.3 rad/s 慢慢回零
手夹住东西 在数据手套图形上位机点红色「STOP · 停止真机映射并张手」 → 手立刻张开；或直接拔手套 USB 接收器（0.5 秒后自动张开）
想整套停掉 终端 A Ctrl+C —— 自动「手张开 → 手臂回零 → 交还控制权」，要几秒

#这些不是急停，别指望它们救场

  • 终端 A Ctrl+C 是优雅退出：手张开 → 双臂 3 秒回零 → armsdk 权重渐降到 0。 整个过程要好几秒，机器人在这期间还在动。
  • 终端 B 按 Q 只是关上位机。手臂那边要等 1 秒超时才开始慢速回零， 手要等 0.5 秒断流才张开。
  • 拔网线 / 关 WiFi 等价于上一条，靠的是接收端的超时兜底，不是主动停止。

这些兜底机制本身是可靠的（断流必张开、超时必回零、退出必交还控制权）， 但它们的设计目标是「链路断了别出危险」，不是「零点几秒内制动」。

#1.5 · 通用：三个终端

终端 在哪 跑什么
A 🤖 板载机（SSH unitree@192.168.3.78，密码 123） 接收端
B 💻 PC 上位机：IMU 解算、3D 界面、发指令
C 💻 PC 手套（只有用到灵巧手时才需要）

顺序永远是 A → B → C。 手套的 TCP 连接是在图形安全面板点「ARM 并启动」时才建立的， 连不上就退出、不重试。

#关于力反馈手套的 --hand both --hand-haptic --hand-touch-hz 10

机器人力反馈触觉端口按手分，--hand 点名哪只才 bind 哪只：

--hand bind 的触觉端口
right 只有 9201
left 只有 9202
both 9201 + 9202

所以下面每一节的终端 A 都写 --hand both --hand-haptic --hand-touch-hz 10，哪怕那一节只遥操 一只手、甚至根本不用手。没数据的那只手不会乱动 —— 接收端每帧都收到「没数据」， 一直朝张开走（hands = result.get("hands") or {} → update(None)）。

数据手套图形上位机不连接这两个端口，也不会震动。 这一节的所有触觉参数都只是为机器人端力反馈手套保留。

--hand-haptic 必须配 --hand，所以连"只跑手臂"的几节也得给 --hand both， 否则 argparse 直接报错。

起来后另开一个 SSH 窗口验证：

ss -ltnp | grep -E "920[12]|930[12]"

要看到 9201 和 9202 各一行 LISTEN。

代价：力反馈触觉读跑在 50Hz 控制线程的同一条 socket 上，会让手指动作偶尔顿一下。 下面每条命令都写死 --hand-touch-hz 10（默认 5）。觉得顿就往下调，--hand-touch-hz 1 是最省的一档。不用力反馈手套就把 --hand-haptic 去掉，其余不变。

#每次起接收端之前，先查旧进程（手乱动的头号原因）

-9 跳过退出流程，手停在当时的握持姿态上不张开。 pkill -f robot_arm_receiver 会连你自己的 SSH 会话一起杀掉。

#2 · 连接机器人（SSH / WiFi / 网线）

机器人上有两张网，分清楚，这是最常见的困惑来源：

① 外部网络（WiFi 或 网线接路由器）        ② 机器人内网 192.168.123.x
   PC、5 个 IMU、机器人 wlan0                板载机 .164、主控 .161
                                             因时右手 .211、因时左手 .210

灵巧手永远在 ② 上，PC 永远够不着它。 所以手的驱动跑在板载机上，PC 只通过 UDP 发闭合度。这是架构前提，不是妥协。

#2.1 · 走 WiFi（默认，全无线）

ssh unitree@192.168.3.78

密码 123。加 keepalive 防止长时间不敲命令被断： ssh -o ServerAliveInterval=30 unitree@192.168.3.78

前提：PC、5 个 IMU、机器人必须在同一个 SSID 下（IMU 发现走 UDP 4212 广播， 跨网段失效）。优先 5GHz。

连上之前先测一下无线够不够用：

ping -c 40 -i 0.2 192.168.3.78
# 好的结果：0% 丢包，avg < 10ms，max < 25ms

⚠️ 绝对不要给接收端加 --iface wlan0。 接收端跑在机器人上，DDS 全程在机器人 内部走 eth0，WiFi 上只有 UDP 9527，这是安全的。--iface wlan0 会把 DDS 本身架到 WiFi 上，500Hz 实时流一抖就断控。

#ping 不通 = IP 变了

G1 的 WiFi 地址走 DHCP，重启后会变（2026-08-04 就从 .85 变成了 .78）。

手边能看到 G1 终端的话最快：

ip -4 addr show | grep 'inet 192.168.3'

只能从 PC 找的话，三步。先扫网段：

for i in $(seq 1 254); do (ping -c1 -W1 192.168.3.$i >/dev/null 2>&1 && echo "192.168.3.$i UP") & done; wait

再看谁开了 22 端口：

for ip in <上一步列出的地址>; do timeout 1 bash -c "</dev/tcp/$ip/22" 2>/dev/null && echo "$ip:22 OPEN"; done

最后这步才是决定性的 —— G1 板载机的 80 端口跑着宇树自己的升级页：

curl -s --noproxy '*' http://<候选IP>/ | grep -o '<title>[^<]*</title>'
# G1 会返回：<title>unitree-upgrade</title>

同网段的 192.168.3.76 是树莓派（Debian 12，MAC 前缀 2c:cf:67），别登错。 G1 是 Ubuntu 20.04。

拿到新 IP 后，本手册里所有 192.168.3.78 都要跟着换。

# 姿势 要点
1 比赞（四指弯到抓握深度，拇指笔直朝上竖起） 四指弯到你平时遥操会握到的深度
2 四指伸直并展开 不要弯指，手腕手掌不要转

#做完看这一行判断标得好不好

[指腹重定向] 横贴掌心位移=xx.x mm  OK 位移=xx.x mm  两手势夹角=xx.x 度

#怎么用：盯住 0.9 秒就锁定

准星（视野正中那个十字）的颜色就是状态：

准星颜色状态含义
灰SEARCHING没找到目标，把准星移到物体上
黄选中中 n%正在数 0.9 秒，同时物体上出现细白边
绿TARGET LOCKED锁定，物体上变成粗红边，下方出现左右手距离
橙切换目标 n%准星移到了别的物体上，数 1.35 秒才切过去
黄暂时看不到目标被挡了一下，报的还是最后一次好读数，撑 1 秒
红目标丢了撑不住了，回到 SEARCHING

换目标故意比首次锁定更难（1.35s vs 0.9s）：获得锁要容易、丢掉锁要难， 否则准星扫过别的东西就被抢走。

锁的是三维点不是像素，所以腰一转、身子一晃，锁不会跟丢。手柄 握持键可以手动解锁。

#红边是怎么来的：准星指哪就分割哪

准星那个像素直接喂给 MobileSAM，它返回那一点所属物体的 mask，取轮廓下发。不做目标检测、不认类别 —— 桌上的电源盒、接线端子、 胶带、急停按钮，COCO 那 80 类里一个都没有，走 YOLO 是描不出来的。

阶段板载实测说明
编码器（整帧）99.7 ms按 5Hz 跑，物体不会跑
解码器（一个准星点）9.4 ms准星一动只重跑这个，不重编码整帧
轮廓提取1.0 ms

吃的是 GPU，而视频编码走 CPU 上的 VP8，两者不抢。 分割挂了也只是没有红边，画面和距离一点不受影响。

准星落在空桌面上时描出来的就是那片桌面 —— 这是对的，那里本来就没有物体。 要描物体就把准星压到物体上。

#7.5 · 更快响应（--response-mode）

跟手不够、感觉手臂"拖"了一拍，先调这个，不要去调 IK。

上位机在方向向量上有一道自适应低通：动得慢时截止频率低（滤得狠、稳但迟钝）， 动得快时自动放开。--response-mode 换的就是这条曲线，除此之外不影响任何东西 （发送端没有第二道平滑，机器人端一个字不用改）。

模式 静止时截止 静止群延迟 快速运动截止 运动群延迟
original（默认） 2 Hz 80 ms 10 Hz 16 ms
balanced 4 Hz 40 ms 30 Hz 5 ms
fast 8 Hz 20 ms 45 Hz 3.5 ms

对比一下别的环节：IK 中位 5 ms、IMU 数据年龄约 10 ms、50 Hz 发送量化 0~20 ms。 慢速动作时这道滤波是最大的一项，是 IK 的 16 倍。

⚠️ 代价是平滑变少，IMU 抖动会更直接地传到机器人手臂上。 链路不稳的时候别开 —— 先按 10 章确认 ping 的 max < 30 ms。 建议顺序：original 标定并跑通 → 换 balanced → 还嫌迟钝再上 fast。 一次只改这一个参数，别和别的改动叠在一起试。
