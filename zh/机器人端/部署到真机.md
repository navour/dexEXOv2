# 部署到 G1 真机

本文只讲**机器人端**怎么上真机。IMU 佩戴与校准流程见根目录 `README.md`。

---

## 0. 先搞清楚一件事：两种控制接口

`robot_arm_receiver.py` 现在有两种真机控制模式，选错会摔机器人。

| | `--mode armsdk` **(默认)** | `--mode lowcmd` |
|---|---|---|
| DDS 话题 | `rt/arm_sdk` | `rt/lowcmd` |
| 接管的电机 | 腰 12~14 + 双臂 15~28 | **全部 29 个，含双腿** |
| 双腿 / 平衡 | 官方运控服务负责 | **无人负责** |
| 运控服务 | **必须运行** | **必须停止** |
| 机器人姿态 | **可以站在地上** | **必须吊装悬空** |
| 用途 | 正常遥操 | 全身增益调试 |

`armsdk` 通过 `motor_cmd[29].q` 这个 0~1 的权重位把双臂指令**混入**官方控制器，
腿部指令一个字节都不发，所以官方平衡控制完全不受影响。这是 G1 做手臂遥操的标准做法，
和官方 `g1_arm7_sdk_dds_example` 用的是同一套接口。

**第一次上真机请一律用默认的 `armsdk`。**

## 1. 前置条件

- [ ] 整条链路已经在仿真里跑通过（`仿真/g1_mujoco_sim.py`，见根目录 README）

- [ ] 遥控器在手边，随时能按 **L2+R2** 进阻尼态
- [ ] 急停开关可达

## 2. 网络

接收端可以跑在两个地方，网络配置不同。

### 方案 A：跑在机器人板载计算机上（推荐）

```bash
ssh unitree@192.168.123.164     # G1 板载开发计算机默认 IP
```

DDS 走本机内网，**不需要 `--iface`**。
发送端（PC/树莓派）和机器人必须能互通 —— 通常是机器人和 PC 都接同一台路由器。

### 方案 B：跑在外部 PC / 树莓派上

外部机器用网线接入机器人的 123 网段，配静态 IP：

```bash
sudo ip addr add 192.168.123.99/24 dev eth0
ping 192.168.123.161            # G1 主控, 通了才继续
ip -br addr                     # 记下网卡名, 下面 --iface 要用
```

这种情况**必须**加 `--iface eth0`（换成实际网卡名），否则 DDS 连不上。

> 自动发现（UDP 9528 广播 `G1RC,...`）在机器人有多张网卡时可能广播出错误的 IP。
> 发送端连不上就别用自动发现，直接 `--udp-target <机器人IP>:9527`。

两张网（路由器 LAN 跑遥操 UDP、123 网段跑 DDS）的区别、连通性自检脚本、
以及从 PC 远程调试的完整流程，见 [第 8 节](#8-从-pc-远程调试)。

在**运行接收端的那台机器**上装（板载机通常已经装好，先验证一下）：

```bash
cd unitree_sdk2py && pip3 install -e .
```

把 `export CYCLONEDDS_HOME=...` 写进 `~/.bashrc`，否则重新登录后又找不到。

## 5. 空载测试（机器人站立，不接 IMU）

这一步只验证 DDS 通了、权重渐入正常、手臂不乱动。

**5.1 让机器人站起来**

遥控器：`L2+B`（阻尼）→ `L2+↑`（准备）→ `R1+X`（起身）。
机器人稳定站立、运控服务在跑，这是 `armsdk` 的前提。

**5.2 启动接收端**

```bash
cd ~/teleop
python3 robot_arm_receiver.py                    # 板载机
# 或外部 PC:
python3 robot_arm_receiver.py --iface eth0
```

正常输出：

```
  控制接口: armsdk (rt/arm_sdk)
[+] 运控服务 (sport_mode) 正在运行, arm_sdk 可用, 双腿平衡由官方服务负责
[+] 指令发布话题: rt/arm_sdk
[+] 已连接到机器人 (mode_machine=5)
[*] 启动阶段: 3.0s 缓慢接管...
```

**这时机器人手臂应该纹丝不动**（3 秒内权重 0→1，目标就是当前实测位置）。
状态行里 `[armsdk w=1.00]` 表示已完全接管。

如果看到 `[!] 运控服务未运行` —— 说明机器人还在阻尼态，回 5.1。

**5.3 确认能安全退出**

按 `Ctrl+C`。应该看到双臂缓慢回零 → `[*] 交还手臂控制权 (2s 渐出)...` → `[+] 已安全退出`。
退出后手臂重新归官方运控服务管，此时推一下手臂应该有正常的伺服阻力。

## 6. 接入 IMU 正式遥操

**6.1 机器人端先起**（同 5.2，保持运行）

**6.2 发送端**

PC：

```bash
cd PC端 && source .venv/bin/activate
python3 dual_arm_viz.py --udp-target <机器人IP>:9527
```

树莓派：

```bash
cd 树莓派端 && source .venv/bin/activate
python3 headless_arm_sender.py <机器人IP> 9527
```

**6.3 上电顺序**

1. 等 IMU 连满 5/5
2. 穿戴好 → 按 `C` 走完 4 步校准（**这一步机器人还处于 mode=0 回零态，不会动**）
3. 校准完，**先只放开一条手臂**：按 `R` 选右臂 → `SPACE` 开始跟随
4. 小幅度动一下，确认方向对、无抖动
5. 再按 `L` + `SPACE` 放开左臂

**6.4 随时能停**

| 动作 | 效果 |
|---|---|
| 发送端 `SPACE` | 当前手臂停止跟随，缓慢回零 |
| 关掉发送端 | 1 秒超时后机器人自动回零 |
| 接收端 `Ctrl+C` | 回零 + 交还控制权给运控服务 |
| 遥控器 `L2+R2` | 全身阻尼，最后的保险 |

## 6.5 腰部跟随（`--waist`，默认关闭）

armsdk 本来就接管腰 12/13/14（官方 `g1_arm5_sdk_dds_example` 的 `arm_joints`
里就有这三个），平时它们被恒定拉回中位。加 `--waist` 后，胸/腰 IMU 的
左右扭转会驱动 `waist_yaw`：

```bash
python3 robot_arm_receiver.py --waist            # 板载机
```

发送端也要开：PC 端加 `--waist`，或运行中按 `Shift+W` 切换。**两边都开才生效**
——机器人端不信任发送端，自己再夹一次限位。

> **只有 PC 端能发腰。** 树莓派端发的还是 45 字节的旧 `UARM` 包，里面没有腰
> 部字段，所以从树莓派遥操时 `--waist` 不会有任何效果。这种情况状态行会显示
> `腰:--(发送端不支持)`，不会假装在跟随。

只驱动 `waist_yaw`。`waist_roll/pitch` 恒定为 0：它们限位只有 ±0.52 rad，
且直接改变上半身重心在矢状/冠状面的投影，对运控服务是比 yaw 强得多的扰动。

| 防线 | 值 | 在哪 |
|---|---|---|
| 发送端夹紧 | ±1.0 rad | `PC端/waist_tracker.py` |
| 接收端再夹 | ±1.0 rad（URDF 是 ±2.618） | `waist_follow.WAIST_YAW_LIMITS` |
| 接收端限速 | 1.5 rad/s（手臂是 5.0） | `waist_follow.WAIST_FOLLOW_SPEED` |
| 松手即回中 | `mode=0` / 超时 / 尾块丢失 | 与双臂回零同步 |

**第一次开腰的顺序**：机器人先站稳 → 只开右臂跟随确认正常 → 再加 `--waist`
重启接收端 → **小幅度**扭腰（±15° 以内）看跟随方向和延迟 → 逐步加大。
扭腰改变上半身重心，运控服务会当成扰动来补偿，幅度大 + 速度快时脚下会有
明显调整动作。旁边留人扶。

状态行会显示 `腰:+23°`；显示 `腰:+0°(回中)` 说明门控开着但没收到有效尾块
（发送端没开 `--waist`，或还没采腰部零位）。

## 7. lowcmd 全身模式（仅吊装）

**只有机器人挂在吊架上、双脚完全离地才能用这个模式。** 它会把双腿和腰拉到零位，
且没有任何平衡控制。

```bash
python3 robot_arm_receiver.py --mode lowcmd --iface eth0
```

程序会打印警告并要求交互确认，然后询问是否停止运控服务
（`ReleaseMode`，**机器人会立刻失去平衡瘫软**）。确认前请再检查一次吊装。

脚本化场景可以用 `--yes` 跳过确认 —— 但请只在确认吊装到位后才加。

> **本机 SDK 没有 MotionSwitcher（2026-07 实测）。** 机载机上的
> `unitree_sdk2py` 里不存在 `MotionSwitcherClient`（只有一个同名的 IDL
> 消息），因此本程序在这台机器上**既查不到、也停不掉运控服务**：
>
> - `armsdk`：只会提示"无法查询"。不危险 —— 运控没起的话 `arm_sdk` 单纯
>   不生效，机器人不动而已。启动后完全不动，八成就是这个原因。
> - `lowcmd`：**会拦下来要求你确认**。这一步不能跳 —— 若运控此刻仍在运行，
>   它会和 `rt/lowcmd` 同时写同一批电机，两个控制器互相打架。必须先用遥控器
>   让机器人进入调试/阻尼态，确认官方运控已交出电机控制权。

### 7.1 起身与状态机：用 `g1_ctl.py`

遥控器的 `L2+B` / `L2+上` / `R1+X` 背后都是 `LocoClient` 的 RPC，`g1_ctl.py`
把它们做成了 SSH 命令，并强制检查状态机顺序：

```bash
python3 g1_ctl.py status      # 只读，任何模式下都能看
python3 g1_ctl.py damp        # == L2+B      (FSM 1)
python3 g1_ctl.py prepare     # == L2+上     (FSM 4)
python3 g1_ctl.py start       # == R1+X      (FSM 200)
```

**调试模式下它和遥控器一样失效**，所有命令返回 `code=3102` —— 调试模式的定义
就是停掉运控服务，而这些指令全是发给它的。详见 `快速上手_真机遥操.md`。

## 8. 从 PC 远程调试

### 8.1 两种"远程"，别混

| | **SSH 远程**（推荐） | **DDS 远程** |
|---|---|---|
| 接收端跑在 | 机器人板载机 | 你的 PC |
| PC 的角色 | 只是个终端 | 实际控制器 |
| 启动命令 | `python3 robot_arm_receiver.py` | `python3 robot_arm_receiver.py --iface eth0` |
| DDS 链路 | 板载机内部，零跳 | PC ↔ 机器人，多一跳网络 |
| 网络抖动后果 | 只是你看不到输出，控制不受影响 | **控制指令断流** |
| 改代码 | 要 rsync 过去 | 存盘即生效 |
| 适用 | 正式遥操、长时间运行 | 改解算逻辑、加打印、单步调试 |

**判断标准很简单：网络断了会不会影响机器人。** SSH 远程断线只影响你的终端；
DDS 远程断线等于控制器掉线。所以 `--mode lowcmd` 永远不要用 DDS 远程跑。

### 8.2 接线与连通性

调试时最容易搞混的是：系统里同时有**两张网**，跑的是完全不同的东西。

```
  ① 路由器 LAN (192.168.3.x)            ② 机器人内部有线网 (192.168.123.x)
                                           网线直连机器人网口，DDS 专用
  PC ────┐                               PC ──网线── 机器人网口
  IMU×5 ─┼─ 路由器 ─── 机器人             .222          .164 板载开发计算机
  树莓派 ─┘                                              .161 主控

  跑: IMU 四元数 UDP 4211                跑: rt/lowstate
      遥操指令   UDP 9527                     rt/arm_sdk / rt/lowcmd
      发现广播   UDP 9528                     (CycloneDDS)
```

**`--iface` 只跟 ② 有关，`--udp-target` 只跟 ① 有关。** 把这两个搞混是最常见的连不上原因。

#### PC 和机器人都连 WiFi：可以，但只限 SSH 远程

日常调试推荐这么干。哪条链路能走 WiFi：

| 链路 | 走 WiFi | 说明 |
|---|---|---|
| SSH / rsync / VS Code Remote-SSH | ✅ | 断了只是你看不到输出，控制不受影响 |
| 遥操指令 UDP 9527 | ✅ | 50 Hz，丢包有 1 秒超时回零兜底 |
| 自动发现广播 UDP 9528 | ⚠️ | 路由器开了 AP 客户端隔离就收不到，改用 `--udp-target` |
| **DDS（`--iface wlan0`）** | ❌ | ② 网跑的是 500 Hz 实时流，WiFi 抖动直接变成控制断流 |

**关键**：SSH 远程时接收端跑在板载机上，DDS 走的是机器人**内部**的 ② 网，零跳。
WiFi 上只走终端字符。所以"两边都连 WiFi + SSH 进去跑"完全安全，
危险的只有 `--iface wlan0` 这种把 ② 网本身架到 WiFi 上的做法。

板载机连上 WiFi 后，SSH 要用它在 ① 网的地址，**不是** `192.168.123.164`：

```bash
# 板载机上（首次用网线或接显示器配）
nmcli device wifi connect "<SSID>" password "<密码>"
ip -br addr                      # 记下 wlan0 的地址，例如 192.168.3.85
```

```bash
# PC 上
ssh unitree@192.168.3.85         # 机器人在路由器下的 IP
```

两个地址指的是同一台板载机的两张网卡：`192.168.3.85` 在 ①，
`192.168.123.164` 在 ②。PC 走 WiFi 访问不到 ②。

配好之后就可以拔掉网线，全程无线：

```bash
# 机器人上
ssh unitree@192.168.3.85
tmux new -s teleop
cd ~/teleop && python3 robot_arm_receiver.py      # 板载机跑，不需要 --iface

# PC 上（同一台路由器下）
cd PC端 && source .venv/bin/activate
python3 dual_arm_viz.py --udp-target 192.168.3.85:9527
```

无线跑的时候盯住三件事：

1. **PC、5 个 IMU、机器人必须在同一个子网**（同一台路由器、同一个 SSID）。
   IMU 发现（UDP 4212）和机器人发现（UDP 9528）都是广播，跨网段直接失效。
2. **优先 5GHz**。① 网上已经有 5 个 IMU 在 ~100Hz 推四元数，2.4G 很容易被塞满。
3. **看接收端状态行的 `抖动p50/p95/p99`**。p99 持续超过 50ms 就说明 WiFi 撑不住了，
   表现是手臂一顿一顿；断流超过 1 秒会直接触发回零保护。
   这时候给**机器人**插网线接路由器就行，PC 那头继续无线不影响。

#### 网线直连：只有 DDS 远程才需要

要跑 `--iface` 把接收端放在 PC 上时，才需要接 ② 网并配静态 IP：

```bash
sudo ip addr add 192.168.123.99/24 dev eth0
ip -br addr                      # 记下网卡名，--iface 要用

ping -c3 192.168.123.161         # 主控
ping -c3 192.168.123.164         # 板载开发计算机
```

两个都通了再往下走。只通一个通常是网线插错口。

**ping 通不等于 DDS 通。** DDS 单独验一次，收不到帧就别往下走：

```bash
python3 - <<'EOF'
import time
from unitree_sdk2py.core.channel import ChannelFactoryInitialize, ChannelSubscriber
from unitree_sdk2py.idl.unitree_hg.msg.dds_ import LowState_

IFACE = "eth0"          # 在机器人板载机上跑就改成 None

ChannelFactoryInitialize(0, IFACE) if IFACE else ChannelFactoryInitialize(0)
n = [0]
def cb(msg):
    n[0] += 1
    if n[0] == 1:
        print(f"mode_machine={msg.mode_machine}")
        print(f"左肩pitch(15)={msg.motor_state[15].q:+.3f}  "
              f"右肩pitch(22)={msg.motor_state[22].q:+.3f}")
sub = ChannelSubscriber("rt/lowstate", LowState_)
sub.Init(cb, 10)
time.sleep(3)
print(f"3秒收到 {n[0]} 帧 (正常约 1500 帧 / 500Hz)")
EOF
```

收到 0 帧 → 查网卡名、静态 IP、`CYCLONEDDS_HOME`，别急着启动接收端。

遥操 UDP（① 网）那一侧单独验，在**接收端所在的机器**上抓包：

```bash
sudo tcpdump -i any -n udp port 9527 or udp port 9528
```

看得到 9528 出去、9527 进来，说明发现广播和指令流都正常。

### 8.3 SSH 方式：一定要用 tmux

直接 `ssh + python3` 跑，SSH 一断（网线松、WiFi 抖、笔记本休眠）程序就被 SIGHUP 杀掉。
**接收端被杀 = 手臂失去指令**，且不会走 `Ctrl+C` 的回零 + 权重渐出流程。此时机器人处于
什么状态取决于 `arm_sdk` 服务对指令中断的处理 —— **本项目没有验证过这个行为，不要依赖它**。
唯一可靠的结论是：正常退出必须走 `Ctrl+C`。

对照一下，另一种断线是**安全**的：如果断的是遥操 UDP（发送端掉线、路由器抖），
而接收端进程还活着，1 秒超时保护会让手臂自动缓慢回零。危险的只有接收端进程本身被杀。

```bash
ssh unitree@192.168.123.164
tmux new -s teleop               # 首次
cd ~/teleop && python3 robot_arm_receiver.py
# Ctrl+B 然后按 D 脱离，程序继续跑
```

断线后重连接回去：

```bash
ssh unitree@192.168.123.164
tmux attach -t teleop            # 状态行还在滚
```

想在 PC 上另开一个窗口看输出，再 `tmux attach` 一次即可（多个终端可同时 attach）。

### 8.4 DDS 远程方式

只在 `armsdk` 模式、机器人站立且运控服务在跑的前提下用：

```bash
cd 机器人端
python3 robot_arm_receiver.py --iface eth0
```

启动输出里确认这两行：

```
  DDS 网卡: eth0
[+] 运控服务 (sport_mode) 正在运行, arm_sdk 可用, 双腿平衡由官方服务负责
```

发送端此时可以跑在同一台 PC 上（`--udp-target 127.0.0.1:9527`），
整条链路都在你手边，加打印、下断点都方便。

**注意**：接收端在 PC 上时，自动发现广播（UDP 9528）播的是 PC 的 IP，
另一台机器上的发送端会连错。DDS 远程调试时发送端一律显式指定 `--udp-target`。

### 8.5 代码同步

改完 PC 上的代码推到机器人（`-n` 先看会传什么，确认无误再去掉）：

```bash
rsync -avz --delete \
      机器人端/robot_arm_receiver.py 机器人端/teleop_protocol.py \
      unitree@192.168.123.164:~/teleop/
```

VS Code 装 **Remote - SSH** 扩展可以直接连上去改，省掉同步这一步：
`F1` → `Remote-SSH: Connect to Host` → `unitree@192.168.123.164` → 打开 `~/teleop`。

**但不要在 500Hz 控制循环里下断点。** 断点一停，指令流就断了：`armsdk` 模式下权重
停在最后一帧，`lowcmd` 模式下电机保持最后指令，而且回零和超时保护统统不会执行。
要看中间值就加打印，或者事后看轨迹 CSV。

板载机上**不要** `git clone` 整个仓库再 `git pull` —— 板载机磁盘小，
而且 `.git/` 在本仓库是空的，没有历史可拉。

### 8.6 把日志拉回来分析

延迟和抖动问题**必须两端一起看**，单看一端分不清是网络问题还是解算问题。

### 8.7 不碰机器人也能调的部分

改**发送端**逻辑（IK、滤波、校准）完全不需要真机 —— 仿真监听同一个 9527 端口，

### 8.8 红线

- **`--mode lowcmd` 只在 SSH 远程 + 吊装下跑**，绝不 DDS 远程
- **不要用 WiFi 跑 DDS 远程**，丢包直接变成指令断流
- PC 睡眠/锁屏前先确认接收端跑在 tmux 里，或者干脆停掉
- 远程调试时遥控器仍然要在**机器人旁边的人**手上，`L2+R2` 是最后的保险

## 9. 故障排除

| 现象 | 原因 / 处理 |
|---|---|
| `[!] 超时: 未收到机器人状态` | DDS 不通。板载机：确认 `CYCLONEDDS_HOME`。外部机：`--iface` 网卡名写错，或没配 123 网段静态 IP |
| `[!] 运控服务未运行` (armsdk) | 机器人在阻尼态，用遥控器 `R1+X` 起身 |
| armsdk 下机器人完全不动 | 权重没升上去看状态行 `w=`；或者运控服务被别的程序 Release 掉了 |
| 手臂剧烈抖动 | 降 `Kp_full` 里对应关节的增益。注释里写明当前是 v4 实机整定值，仿真值上实机会振荡 |
| 发送端找不到机器人 | 别用自动发现，直接 `--udp-target <IP>:9527` |
| RX 频率远低于 50Hz | 网络丢包，看状态行的抖动 p50/p95/p99 |
| 腰部被拉正 | armsdk 模式确实会把腰 12~14 保持在 0 位，与官方例程一致 |
| 无线下手臂一顿一顿 | WiFi 拥塞。换 5GHz；仍不行就给机器人插网线接路由器（PC 可继续无线） |
| 无线下反复触发回零 | UDP 断流超过 1 秒。同上；先看抖动 p99 确认是网络而不是发送端卡住 |
| `--iface wlan0` 收不到 lowstate | DDS 不能跑 WiFi，组播发现基本会被 AP 拦掉。接收端改回板载机运行 |
| SSH 一断程序就没了 | 没用 tmux，见 8.3 |

轨迹日志在 `log/traj_log_*.csv`，每关节记录 cmd/act/err/vel/tau + UDP 间隔，
调增益时直接看 `*_err` 列。
