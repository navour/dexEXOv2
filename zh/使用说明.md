## D · 单独右手

**手臂一动不动**，不初始化 DDS、不接管任何电机，运控服务没起来也照跑。

**只读，不会让手动。** 要看到全部 `[+]`，最后一行「检查通过」。不通别往下走
（多半是手的网线或没上电）。

**第 2 步**（终端 A）起接收端：
```bash
~/zh/start.sh --hand right --hand-only
```
横幅要看到这三行：
```
灵巧手: right (行程 100%, 断流 0.5s 自动张开)
[!] 大行程: 手指可以完全闭合, 会夹伤; ...
[*] right手驱动已启动 → 192.168.123.211:6000
```

**第 3 步**（终端 B）起上位机：
```bash
/home/hong/unitree/最新直接能用的代码/PC端/.venv/bin/python \
    /home/hong/unitree/最新直接能用的代码/PC端/dual_arm_viz.py \
    --hand \
    --udp-target 192.168.3.78:9527
```
> **不要加 `--real-hand`** —— 手由机器人驱动。两条路同时开会争同一个寄存器。

**第 4 步**（终端 C）起手套：
```bash
/home/hong/unitree/最新直接能用的代码/mhandpro/bin/mhandpro_diagnostic
```
启动时会自己把左右手两份标定读进来，**不用再 `load`**。看到
`六维动作映射已自动加载：.../right_hand.calib` 就对了。

**第 5 步**（终端 C）在 `诊断>` 提示符下敲：
```
use right
teleop /home/hong/unitree/最新直接能用的代码/mhandpro/config/inspire_right_sim.cfg
```
> 只插了右手那只手套的话 `use right` 可以省。两只都开着时 SDK 默认选左手，
> 所以这条不能省。

> **`inspire_*_sim.cfg` 名字里带 sim，但真机也用它**，不是拿错文件了。
> 它把端点设成满量程 0~1000，于是发出来的数就是**闭合度 ×1000**，PC 端除以
> 1000 就得到 0~1 的闭合度，不需要知道任何真手的寄存器端点。真手的行程换算
> 在**板载机**上做（`hand_driver.py`，同样是满量程 + 行程上限）。
>
> 另一份 `inspire_left.cfg` 是给「C++ 直接 Modbus 打到手上」那条老路用的，
> 我们不走那条 —— PC 在 WiFi 上根本够不着 `192.168.123.x` 的手。
>
> 同理，cfg 里那个 `stale_abort_ms=1500` 只管手套→PC 这一段。**真正保命的是
> 板载机上的 0.5 秒断流张开**，跟这个值无关。

**第 6 步** 确认手离开抓握范围，敲：
```
ARM
```
⚠️ **手指立刻开始跟着你动，整程，能完全闭合。**

终端 A 的状态行会出现 `right手:xx%` 跟着变。收工看 L 节。

## F · 双手（不带手臂）

### F1 · 双手力反馈接口

普通双手位置遥操不变。需要树莓派外骨骼闭环时，机器人端命令额外加：

```bash
~/zh/start.sh --hand both --hand-only --hand-haptic
```

| 手 | INSPIRE内网地址 | 触觉TCP | 树莓派覆盖TCP |
|---|---|---:|---:|
| 右 | `192.168.123.211:6000` | 9201 | 9301 |
| 左 | `192.168.123.210:6000` | 9202 | 9302 |

树莓派使用 G1 WiFi 地址 `192.168.3.78` 连入。如果板载机 WiFi IP 变了，
只改树莓派上的 `--force-host`/`--haptic-host`。

力控优先级是逐指的：`FREE/FORCE_ENTRY` 继续跟手套，`LOCKED` 冻结该指
并叠加PID位置增量，`RELEASE/RETURN_SETTLE` 平滑追回手套位置。
树莓派断开或 0.5 s 没有新覆盖包时自动恢复手套跟随。

> 禁止同时运行 Inspire DDS Headless 驱动或
> `standalone_inspire_bridge.py`。左右手的 Modbus 只能由本进程持有。

**第 1 步**（终端 A）两只手都体检：
```bash
cd ~/zh && python3 hand_check.py --side right
cd ~/zh && python3 hand_check.py --side left
```

**第 2 步**（终端 A）
```bash
~/zh/start.sh --hand both --hand-only
```
横幅里应该是 `灵巧手: right+left`，后面跟两行 `手驱动已启动`（`.211` 和 `.210`）。

**第 3 步**（终端 B）两个开关一起给：
```bash
/home/hong/unitree/最新直接能用的代码/PC端/.venv/bin/python \
    /home/hong/unitree/最新直接能用的代码/PC端/dual_arm_viz.py \
    --hand --hand-left \
    --udp-target 192.168.3.78:9527
```
界面里会同时画出左右两只手（24 个手指关节）。

**第 4 步**（终端 C）
```bash
/home/hong/unitree/最新直接能用的代码/mhandpro/bin/mhandpro_diagnostic
```
必须看到 `手套已连接：BOTH`。只显示一只的话另一只没开机或没配对，先解决。

**第 5 步**（终端 C）**一个进程同时驱动两只手** —— 右手配置在前，左手在后：
```
teleop both /home/hong/unitree/最新直接能用的代码/mhandpro/config/inspire_right_sim.cfg /home/hong/unitree/最新直接能用的代码/mhandpro/config/inspire_left_sim.cfg
```
> **不能开两个 `mhandpro_diagnostic` 进程。** 两只手套共用一个 USB 接收器和同一个
> `/dev/ttyUSB0`，第二个进程会卡在串口上打不开。双手必须走 `teleop both`。
>
> 这里不需要 `use` —— `teleop both` 两侧各走各的端口、各自的标定和看门狗，
> 一只手套出故障只会让那一只张开，另一只继续跟随。

**第 6 步** 手离开抓握范围，敲 `ARM`。

## J · 加上腰部跟随

可以叠在上面**任何一节**上。腰用的就是**胸部那个 IMU**，不需要额外传感器。

**改两处命令，加两个按键。**

**改法 1**（终端 A）接收端加 `--waist`：
```bash
~/zh/start.sh --hand both --waist          # 按你那一节的 --hand 参数照抄，末尾加 --waist
```

**改法 2**（终端 B）上位机也加 `--waist`：
```bash
/home/hong/unitree/最新直接能用的代码/PC端/.venv/bin/python \
    /home/hong/unitree/最新直接能用的代码/PC端/dual_arm_viz.py \
    --hand --hand-left --waist \
    --udp-target 192.168.3.78:9527
```
> **两端都要加。** 机器人端不加，上位机发了也没用（`allow_waist` 是硬门控）；
> 上位机不加，机器人端状态行会显示 `腰:--(发送端不支持)`。

**加的两步（必须在手臂已经跟随之后做）：**

**倒数第 2 步**（终端 B）站直、面朝正前方、身体不要扭 → 按 **`W`** 采腰部零位。

**最后一步**（终端 B）按 **`Shift+W`** → 日志「腰部跟随: 开启」，然后**小幅度**
左右扭腰，终端 A 的 `腰:` 要跟着变。

⚠️ **第一次从 ±15° 以内开始，旁边留人扶。** 扭腰改变上半身重心，对运控服务
是真实扰动。

跟随太迟钝用 **`]`** 加增益、**`[`** 减增益（每次 0.1）。
> 实测：发送端能交付原始 IMU 偏转的 0.944，夹位只在 0.4% 的帧上触发、限速
> 0.17% —— 瓶颈不在它们身上，**调增益是对的，不用去改限位**。

腰的状态行怎么读：

| 状态行显示 | 意思 |
|---|---|
| `腰:关(--waist)` | 门控没开，腰保持回中 |
| `腰:+3°(回中)` | 门控开了，但本帧没收到有效尾块 / 手臂还没跟随 |
| `腰:+12°` | **正在跟随** |

**只有 `waist_yaw`（左右扭）会动。** 前后倾和左右倾永远送 0 —— 它们限位只有
±0.52 rad，且直接改变上半身重心在矢状/冠状面的投影，对运控是比 yaw 强得多的
扰动。接收端还会独立把 yaw 夹到 **±1.0 rad**、限速 **1.5 rad/s**，不管上位机
夹过没有。

## 35 · 手套：五姿势映射标定（双手一起，`mapcal both`）

这一步把「你的手在做什么」映射成因时的六个通道。**换操作员、换手套尺寸、或者
觉得手指/拇指跟不对，就重做这一步。**

```
诊断> mapcal both
```

**双手同时摆同一个姿势**，每个姿势依次采两只手，采完之前都不要动。五个姿势：

| # | 姿势 | 要点 |
|---|---|---|
| 1 | **比赞**（四指弯到抓握深度，拇指笔直朝上竖起） | 四指弯到你**平时遥操会握到**的深度 |
| 2 | 四指伸直并展开 | 不要弯指，手腕手掌不要转 |
| 3 | 只做拇指弯曲 | |
| 4 | **拇指横贴掌心** | 四指伸直并拢，拇指横扫过掌心并**真的贴到掌心上** |
| 5 | **OK 手势** | 拇指指腹**捏住**食指指腹 |

**第 1 步的握拳深度就是闭合度 1.0 的位置。** 之后所有通道都是这个深度和张开
之间的线性插值 —— 标得比日常深，用起来就会觉得手指弯得不够。

**为什么是这三个手势（1、4、5）**：它们各自对应因时一个**已知的**目标姿态，
而且都有明确的触觉终点（拇指贴到掌心、两个指腹捏在一起），比「向外张开到某个
程度」可重复得多。以前用「纯对掌」标过，那个动作没有终点，标出来的轴方向甚至
和实际抓握时拇指走的方向大致相反（右手投影 −0.88），两只手还标得不一致。

**做完看这两行**，是判断标得好不好的依据：
```
[指腹重定向] 横贴掌心位移=xx.x mm  OK 位移=xx.x mm  两手势夹角=xx.x 度
```
- **夹角**是关键。因时自己这两个锚点方向的夹角是 **28.7°**，你的应该在这个数
  附近（实测右手 33.4°、左手 30.0°，很好）。
- 夹角明显偏小（比如 < 20°）说明第 4 步拇指没真的贴到掌心，重做。

全部合格后自动覆盖保存到 `config/right_hand.calib` 和 `left_hand.calib`，
下次启动自动加载，**不用手动 `save`**。

> **为什么一定要 `mapcal both` 而不是分别 `mapcal`**：分开标最典型的后果是一只
> 手的展开轴采到了、另一只没采到，用起来就是「同样的动作两只手感觉不一样」。
> `mapcal both` 和单手 `mapcal` 走的是同一份实现，只是一次把两只手的阈值和
> 合格判据一起过一遍，两只不可能漂开。

> 标定文件格式是 `MHANDPRO_CALIBRATION_V4`。老的 V2/V3 仍然能读，但**不会启用
> 拇指指腹重定向** —— V3 的三个点是按老的「张开/纯弯曲/纯对掌」采的，按 V4 的
> 手势语义去读不会报错，只会悄悄错，而这份数据是要驱动真手的。跑一遍
> `mapcal both` 就升级了。

## 36 · 拇指为什么单独有一套（背景，不用操作）

四根手指是一对一的，人手弯曲范围（132–157°）和因时的 ∠α 行程（156°）几乎 1:1，
所以跟得很准。**拇指不一样** —— 人的拇指 4 个以上自由度要压到因时的 2 个
（对掌 ∠β / 弯曲 ∠θ）。

早期版本在**旋转特征空间**里分解这两个自由度，实测两条轴只差 31.5°（右）/
36.8°（左），相关性 0.853/0.801，最小二乘是病态的 —— 症状就是「四指跟得挺好，
拇指位置不对」。

现在改在**指腹位置空间**里分解（同样两个自由度夹角 60.2°，相关性 0.498），
条件数好一个量级。手套那端算好归一化坐标，跟在遥操 JSON 里发过来，PC 端只做
一次纯算术换算。

**拇指弯曲刻意不往抓握方向放大**：四指半闭时指腹间距在（弯曲 0.5，对掌 1.0）
是 16.4 mm，到（弯曲 1.0，对掌 1.0）反而张到 49.1 mm —— 拇指过度弯曲会从手指
旁边划过去，而不是握得更紧。

所以**「四指弯得很深，但拇指够不着」时，先怀疑四指闭合度饱和了**（闭合度 1.0
就是 `mapcal` 第 1 步那个拳头），而不是拇指。四指完全闭合时指尖是贴在掌心的，
任何拇指姿态都够不着（60 mm）。

`--no-thumb-retarget` 可以关掉重定向做 A/B 对比，拇指会退回线性投影。

# 第四部分：网络连接

机器人上有**两张网**，分清楚，这是最常见的困惑来源：

```
① 外部网络（网线接路由器 或 WiFi）      ② 机器人内网 192.168.123.x
   PC、5 个 IMU、机器人 wlan0              板载机 .164、主控 .161
                                           因时右手 .211、因时左手 .210
```

**灵巧手永远在 ② 上，PC 永远够不着它。** 所以手的驱动跑在板载机上，PC 只通过
UDP 发闭合度。这是这套架构的设计前提，不是妥协。

## 41 · 网线直连（最稳）

💻 **PC**
```bash
ip -br addr                                            # 先看有线网卡名
sudo ip addr add 192.168.123.222/24 dev enp0s31f6      # 网卡名按实际改
ping -c3 192.168.123.164                               # 通了才继续
```

**PC 还要同时连 IMU 那个 WiFi** —— IMU 数据只到 PC 为止，机器人不需要连 WiFi。

这时第一部分所有命令里的 `192.168.3.78` 换成 `192.168.123.164`。

> 同网段的 `192.168.123.161` 是主控，能 ping 通但**不开 SSH**，别连错。

## 42 · 全无线（PC、IMU、机器人同一个 WiFi）

**第一部分默认就是这条路**（`192.168.3.78`）。首次要用网线或显示器进机器人配
一次（需要 sudo，密码 `123`）：

🤖 **机器人上**
```bash
sudo nmcli device wifi connect "你的WiFi名" password "你的WiFi密码" ifname wlan0
ip -br addr show wlan0                                 # 记下地址，例如 192.168.3.78
```

这条 profile 会持久化，机器人重启自动重连（已实测）。

**前提：PC、5 个 IMU、机器人必须在同一个 SSID 下**（发现广播跨网段失效）。
优先 5GHz。

无线是否够用：

```bash
ping -c 40 -i 0.2 192.168.3.78
# 好的结果：0% 丢包，avg < 10ms，max < 25ms
```

> **绝对不要给接收端加 `--iface wlan0`。** 接收端跑在机器人上，DDS 全程在机器人
> 内部走 eth0，WiFi 上只有 UDP 9527，这是安全的。`--iface wlan0` 会把 DDS 本身
> 架到 WiFi 上，500Hz 实时流一抖就断控。

> 改完代码记得删 `__pycache__`，板载机是 Python 3.8，旧 pyc 会顶掉新文件。

把环境写死，谁来跑都一样。

# 第六部分：查错

## 61 · 出事怎么办

| 情况 | 动作 |
|---|---|
| 手臂乱动 | 遥控器 `L2+B`；或终端 D `python3 g1_ctl.py damp`；或终端 A `Ctrl+C` |
| 手夹住东西 | 终端 C 敲 `STOP`；或 `Ctrl+C` 关终端 A（退出时先张开手） |
| **全面失控** | **物理急停按钮。** 软件 damp 走 DDS，网线一松 / WiFi 一抖就到不了 |

**建议常开一个 SSH 窗口（终端 D），停在 `python3 g1_ctl.py damp` 上不回车。**

⚠️ `g1_ctl.py damp` 在**调试模式下无效**（返回 3102）—— 那时候只有物理急停。

## 62 · `--mode lowcmd` 那两次确认里的第二问是什么

`--mode lowcmd` 启动时会说「无法查询运控服务状态」。原因：本机
`unitree_sdk2py` 的 MotionSwitcher 实际在 `unitree_sdk2py.comm.motion_switcher`，
而接收端的候选路径表里没列这一条，所以查不到。

**可以放心答 yes 的依据**：你有独立证据 —— `g1_ctl.py status` 返回 `code=3102`，
说明运控服务确实没在跑；而且调试模式是你自己进的。

这个提示是保守设计（查不到就多问一次），不是故障。

## 63 · 灵巧手的四条安全线（都与行程比例无关）

改 `--hand-range` 不影响这四条：

1. **没数据 → 张开**，不是保持。手套断连、上位机退出、WiFi 掉线都走这条
2. **断流 0.5 秒自动张开**（比手臂的 1 秒短 —— 手指夹住东西比手臂停半空更急）
3. **限速 60 counts/帧**，50Hz 下约 0.33 秒走完全程；断流回张也是渐变的
4. **退出时先张开再断开**；断链期间内部状态继续朝张开推进，所以重连后第一帧是
   张开，不会突然接上之前的握持

手的 Modbus 跑在**独立 50Hz 线程**上，不会阻塞 500Hz 的手臂控制周期 —— 手断电时
一次 socket 往返要阻塞到超时，绝不能让它卡住手臂。

**双手时两只手各一个线程、各一条连接、各一个看门狗**，一只出问题只张开那一只。

## 64 · 常见问题

| 现象 | 原因 / 处理 |
|---|---|
| `g1_ctl.py` 全返回 `code=3102` | 调试模式，运控服务没跑。用 `--mode lowcmd`（要吊装），或退出调试模式 |
| 接收端报 `ModuleNotFoundError: unitree_sdk2py` | 没用 `start.sh` 起。见 43 节 |
| 手臂完全不动（armsdk） | 运控服务没起来，`arm_sdk` 没人消费。确认 FSM=200 |
| 手不动 | 先跑 `hand_check.py`，它把「手能不能通」单独摘出来了 |
| **只有一只手动** | 三处都要成对：终端 A 的 `--hand both`、终端 B 的 `--hand --hand-left`、终端 C 的 `teleop both`。少一处那只手就没数据 |
| 上位机拒绝连真机 | 标定质量差于 20°，重新标定（33 节） |
| IMU 连不上 | PC 和 IMU 必须同一个 WiFi，发现走 UDP 4212 广播 |
| 仿真/机器人收不到包（`有效包=0`） | 终端 B 没给 `--udp-target`。不给的话它在等自动发现广播，什么都不发 |
| 手臂一顿一顿（无线） | 看终端 A 状态行 `抖动p50/p95/p99`。p99 持续 > 50ms 说明 WiFi 撑不住，给**机器人**插网线接路由器即可，PC 可继续无线 |
| 手套报 `BAD_MAG` | 现场重做 `magcal`（34 节）。桌面校准拿到现场用反而更糟 |
| 手套显示 LEFT / 只认一只 | 两只都开着时 SDK 默认选左手。单手用 `use right` 切；双手用 `teleop both` |
| 手套开第二个进程打不开串口 | 正常。两只手套共用一个接收器，**只能开一个进程**，双手走 `teleop both` |
| 手套闲置十几分钟后掉线（`HandConect fail`） | 硬件休眠，不是软件问题。重新插拔接收器或给手套重新上电 |
| 四指跟得好、拇指位置不对 | 重做 `mapcal both`，重点看第 4/5 步和最后那行「两手势夹角」（35 节） |
| 四指弯得很深但拇指够不着 | 先怀疑四指闭合度饱和，不是拇指。见 36 节 |
